# Offerithm 功能需求分析

> 本文为初始分析/方案快照；最新落地状态与验证边界见 [阶段0进展](04-phase0-progress.md)。

本文恢复当前代码可证实的产品范围，并提出后续建议；不把 README 宣称、类型定义或建议当作已经交付的功能。分析日期为 2026-11-12，应用代码未修改。路径与行号对应本次仓库基线，详细证据见 [核心调查](evidence/terra-medium-core.md)、[存储调查](evidence/terra-low-storage.md)、[UI 调查](evidence/luna-medium-ui.md)和[测试调查](evidence/luna-low-tests.md)。

## 1. 产品目标与范围

Offerithm 当前是无需账户、在浏览器本地保存数据的 Offer 比较工具。用户录入工作机会，以年度现金、税费、缴费、生活成本、工时等指标作比较；计算是估算工具，依赖政策和假设，不是已核实的税务申报服务。现有数据在 IndexedDB，而非 localStorage。

本轮只交付需求、架构和实施计划。建议后续优先保证结果与数据可靠，再补齐已建模但没有 UI 的能力。账户、后端、云同步、AI 推荐、招聘管理及移动原生应用均没有现有需求证据，不纳入本计划。CSV 定位为比较报告；是否实现 CSV 导入需单独决定，不能由 README 的笼统表述推导出已经存在此能力。

## 2. 状态与优先级口径

- **已实现**：存在用户可达入口和实现路径；不等于所有边界已验证。
- **仅引擎/模型**：类型或函数支持，但缺少对应编辑/管理入口；导入能携带字段不等于 UI 已支持。
- **缺失**：调查范围内未发现实现。
- **待确认**：业务语义、政策有效性或部署行为仍需证据。

下面的 P0/P1/P2 是本报告提出的优先级，不是历史承诺。P0 为可信结果、数据安全与可用部署的先决问题；P1 为完整核心流程；P2 为有价值但需确认口径的扩展。每项任务的阶段依赖见 [实施计划](03-implementation-plan.md)。

## 4. 关键正确性发现

**年度现金遗漏已由代码和数值推导证实。** 月薪 10000、季度应税组件 3000、无年奖/一次性款项/缴费、默认 2025 税表时，聚合年现金和应税收入为 132000，但 `calculateOffer` 用 `grossMonthly × 12` 计算得到税前 120000；税仍为 4680，税后展示 115320。若该组件为现金且其他假设相同，完整现金应税后 127320，少计 12000。证据为 `src/core/engine/salary.ts:44,63,72` 和 `src/core/engine/index.ts:43,55`。年度组件和组件级 oneTime 存在同一遗漏路径。它可通过导入到达，即使页面没有组件编辑器也不能忽略。

**比较得分与 Offer 身份关联有缺陷。** 列头采用加载顺序，分数行采用排名顺序；排名与输入顺序不同即可错列。静态最小场景为固定 ID `a`/`b` 的 A/B，B 税后现金更高，仅 netCash 权重 100、其他权重 0：输入 A/B 得分应为 0/100，排名输出 B/A，页面却把 100/0 放在 A/B 列。UUID 创建先后不能保证 IndexedDB 主键读取顺序。此为代码推导，未在本次浏览器运行该算例。后续应以 `offerId` 关联，再独立选择展示顺序。详见 UI 调查。此项与评分指标是否合理是两个独立问题。

**生产子路径在本地预览已验证不匹配。** 现有 dist 经 Vite preview 打开 `/Offerithm/` 返回 200、页头页脚可见但 main 为空，导航“我的 Offer”跳到根路径 `/offers`。这是本地生产预览结果；线上 Pages 的服务器回退与发布设置仍未验收。见存储调查追加的运行记录。

**以下暂按风险或待确认处理。** 事务过早报告成功、浅导入校验是静态可证实的设计缺口，但事务中途 abort 等具体后果尚未在本次运行复现；年奖单独计税表、缴费归属、政策过期和线上 Pages 深链接行为需独立验证，不能用“所有测试通过”排除。

## 5. 用户故事与验收标准

| 用户故事 | 验收标准 |
| --- | --- |
| US-01 作为求职者，我要录入并可靠保存一份 Offer，避免重新输入。 | **AC-01**：名称、地区、薪资等输入在保存前按同一领域契约校验；无效字段有定位信息；成功后刷新仍得到相同记录；编辑不生成重复 ID，删除结果与持久化一致。 |
| US-02 作为求职者，我要完整、可解释的现金和税费估算。 | **AC-02**：月/季/年/一次性组件分别有年化样例；税前现金、应税收入、税后现金、缴费及企业成本可对账；不应税组件与外层一次性款项不重复或漏算；舍入和预测中一次性款项的处理有明确规则。 |
| US-03 作为求职者，我要知道政策年份和假设，避免误信示例。 | **AC-03**：结果可看到地区、政策年度/来源、扣除与关键假设；关键政策缺失或未核验时显著标明结果状态；年奖两种方式和税档/缴费上下限有独立来源样例。是否阻断缺政策计算须在实现前定案。 |
| US-04 作为求职者，我要按自己的关注点比较多个机会。 | **AC-04**：排序前后每个指标始终绑定同一 Offer ID；切换情景与权重时不串列；零/相同值、并列、全零权重有可理解行为；说明相对评分与代理指标含义；CSV 与当前情景一致。 |
| US-05 作为录入者，我要中断后恢复草稿。 | **AC-05**：草稿可列出、恢复、删除；恢复不覆盖已保存数据直到正式保存；正式保存后同 ID 草稿的清理策略明确；草稿不被误称已正式保存。 |
| US-06 作为本地数据所有者，我要明确保存是否真正成功。 | **AC-06**：仅事务 complete 后反馈成功；失败保留编辑内容并可重试；区分写入失败与写入成功后列表读取失败；测试 abort、quota、禁用存储、blocked 和多标签升级场景。 |
| US-07 作为更换浏览器的用户，我要可验证地备份和恢复。 | **AC-07**：解析、版本识别、嵌套验证、迁移和冲突预览均发生在写入前；未知未来版本/重复 ID/不合法数值不静默写入；用户确认后整批事务提交，任一失败原数据不变；并发修改需重新核对。 |
| US-08 作为分享结果的用户，我要知道文件包含什么。 | **AC-08**：导出从已提交的数据读取，说明包含 Offer 及不包含项；JSON 往返后领域数据等价；CSV 明确为报告，说明情景、单位及非备份性质，特殊字符处理有测试。 |
| US-09 作为浏览器用户，我要通过实际发布地址正常使用。 | **AC-09**：根路径和配置的 `/Offerithm/` 子路径均验收首页、导航、直接进入子页与刷新；实际 Pages 发布及存储来源变化影响被记录。 |
| US-10 作为键盘或手机用户，我要完成核心流程。 | **AC-10**：键盘完成录入、保存、比较与导入；标签与错误关联，焦点可见；窄屏不丢关键操作，比较表有明确横向浏览方案；不以自动扫描替代人工操作。 |

## 6. 非功能约束与验证目标

保持本地优先，不把 Offer 发往新增服务。持久化格式应独立版本化；引擎为可单测的纯函数，IO、UUID、时间和文件下载留在外壳。正确性优先采用可核对的业务样例和不变量，而非仅提升覆盖率百分比。

性能目标当前没有测量证据，不虚构 SLA。建议在开发前用 1/10/100 份 Offer 建立计算、列表及导入基线，记录设备、浏览器和耗时；再依据真实交互卡顿决定缓存、Worker 或列表优化。目标浏览器和最低版本需要产品确定；需覆盖 IndexedDB、`crypto.randomUUID` 和文件 API。

## 7. 实现前必须定案与可延后事项

P0 定案：政策适用年度和可靠来源、年奖税表口径、完整年度现金组成、金额精度/舍入、比较身份关联。P1 定案：缺政策阻断还是明确估计、导入默认合并与覆盖规则、草稿生命周期、备份是否包含草稿/权重/情景。P2 定案：储蓄中公积金归属、时薪通勤/假期规则、一次性收入预测、稳定/成长/福利代理指标，以及政策编辑器和 CSV 导入是否确有需求。

可先做不依赖口径争议的事务完成语义、输入诊断、身份关联和文档纠偏；不得通过给未知政策填零或默认值来悄悄替用户决定业务含义。
