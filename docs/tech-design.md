# Tech Design｜Offerithm（薪筹）

> **文档版本**：v0.1.0 · **更新日期**：2026-10-16 · **文档状态**：技术方案整理稿（部分实现状态待仓库验证）
> **文档职责**：定义数据模型、架构边界、计算与持久化契约、导入导出设计及技术风险；不重定义产品范围或编写测试用例。
> **关联文档**：[产品需求（权威）](./prd.md) · [测试计划](./test-plan.md)

## 1. 技术目标与范围

技术实现须服务于 PRD 中的 **MVP 闭环**：快速估算 → 正式 Offer → 简版比较 → XLSX 全量数据交换。非 MVP 功能可保留扩展点，但不能仅因类型或接口存在便视作已交付。产品优先级与用户可见口径始终以 [PRD 第 2—5 节](./prd.md) 为准。

### 1.1 已知技术基线

按原技术设计提供的信息，项目采用 React 18、Vite、TypeScript、Tailwind CSS v4、`react-router`、IndexedDB 和 Vitest。现有计算引擎目录为 `src/core/engine`，主入口称为 `calculateOffer(offer, options)`，原材料仅说明其**已部分实现**。本次仅整理文档，**未核验仓库实际版本、接口签名、目录或功能覆盖率**。

### 1.2 架构原则

- **纯前端、本地优先**：无需账号或后端，正式数据以浏览器 IndexedDB 为持久化源，数据库名称按现有方案为 `offerithm`；完整 Offer 不写入 Cookie。
- **计算与存储解耦**：计算引擎接受明确的 Offer、政策与假设输入并返回结果，不直接读取 DOM、路由或 IndexedDB。
- **状态语义明确**：正式事实、编辑草稿、快速估算草稿、模拟情景相互隔离；字段来源与对象状态分别建模。
- **可版本化且可恢复**：数据 schema 和导入格式保留 `schemaVersion`，写入操作应具备明确失败语义和迁移路径。
- **渐进式能力**：核心计算与比较服务先满足 MVP；情景、预测、偏好版本同步等按 PRD 延后。

## 2. 模块边界

| 模块／责任 | 建议边界                                                | 对应产品需求      |
| ---------- | ------------------------------------------------------- | ----------------- |
| 领域模型   | Offer、草稿、工作区、偏好、字段来源、政策类型的共享契约 | PRD-M01～M07      |
| 计算引擎   | 薪资汇总、社保、个税、结果口径；尽可能保持纯函数        | PRD-M03～M05      |
| 比较引擎   | 工作区内指标归一化、权重与排序；不直接修改 Offer        | PRD-M06           |
| 本地仓储   | IndexedDB 读写、事务、schema 升级；屏蔽 UI 直接读写细节 | PRD-M02、M07      |
| 数据交换   | XLSX 序列化／校验／导入冲突预览；JSON 通道独立管理      | PRD-M07           |
| 展示层     | 快速估算、Offer 编辑、结果解释、工作区比较和响应式布局  | PRD-M01、M02、M06 |
| 政策数据   | 按地区／年度管理政策文件及其来源、样例回退与适用范围    | PRD-M04           |

模块名称是责任划分，不是未经核验的代码路径承诺。

## 3. 领域模型与数据一致性

### 3.1 主要对象

| 对象                  | 职责及关系                                                  | 交付说明                             |
| --------------------- | ----------------------------------------------------------- | ------------------------------------ |
| `Offer`               | 全局唯一正式记录；一个 ID 可以出现在多个 `Workspace` 中     | MVP 核心                             |
| `QuickEstimateDraft`  | 在创建 Offer 前暂存估算；可多份并存，不自动成为正式 Offer   | 快速估算属于 MVP；多草稿管理批次待定 |
| `OfferDraft`          | 既有 Offer 的未提交修改；同一 Offer 最多一份                | 高级生命周期按 PRD-F01 排期          |
| `Workspace`           | 引用 Offer ID，保存比较配置；草稿预览选择仅在当前工作区生效 | 简版工作区属于 MVP                   |
| `PreferenceProfile`   | 全局偏好模板，包含标识、版本及删除状态                      | 模板版本管理非 MVP                   |
| `WorkspacePreference` | 工作区偏好快照，可记录关联模板 ID／版本                     | MVP 至少满足局部比较权重             |
| `Scenario`            | 在正式事实之上覆盖、锁定参数的模拟对象                      | 非 MVP                               |
| `LocalSettings`       | 最近工作区、界面设置等轻量持久化配置                        | 按 UI 流程排期                       |
| `RegionPolicy`        | 地区与年度政策，按险种条目表示缴费信息与来源                | 核心政策数据属于 MVP                 |

这些是**概念模型**，不是已经确定的 IndexedDB object store 名称或固定字段布局。

### 3.2 字段来源与对象状态必须分离

字段级 `Provenance` 固定为四值：

```ts
type Provenance =
  "confirmed" | "policy-default" | "system-estimate" | "unknown";
```

对象的正式／草稿／情景状态另行表示，**不得**往 `Provenance` 增加 `draft` 或 `scenario`。金额的数值、来源、适用年度、地区和置信信息应能形成可追溯关系。原技术方案提到 `Uncertain<T>` 等不确定性包装类型；具体编码需与现有领域模型核对后确定。

对关键缺失字段，不应简单用 `0` 冒充已知事实。返回值需区分「真实零值」「未提供」「使用样例回退」「无法完成计算」等含义；对外显示通过 warning、来源说明与置信信息表达，避免产生伪精确结果。

### 3.3 草稿、工作区与保存事务

- `QuickEstimateDraft` 和 `OfferDraft` 的来源、目标及生命周期不同，不能因名字都包含 Draft 而合并成同一种业务对象。
- 创建／更新正式 `Offer` 必须由明确的保存操作触发。保存修改时，将正式数据更新与对应编辑草稿清理放入**同一 IndexedDB 事务**；事务失败时正式数据不变化，草稿也不丢失。
- 多工作区引用同一正式 Offer ID，正式保存后的更新可被各工作区重新读取；`OfferDraft` 的预览选择属于**当前工作区 UI 状态**，不得隐式影响其他工作区的比较结果。
- 恢复、放弃、撤销放弃和批量提交的行为以 PRD-F01 为准；需要保存原编辑／预览状态，短暂撤销不能误恢复为正式数据。
- 支持轻量跨标签页「数据已更新」通知，让其他标签页重新读取；**不构建**编辑锁、租约、接管、复杂协作合并、事件溯源或永久操作日志。
- 会话级撤销／重做按用户动作组织，最多 50 条；关闭页面后历史消失，独立于持久化草稿和正式保存。

上述高级草稿与撤销逻辑属**已确认行为、待排期能力**；不得把其技术描述误读为 MVP 全部实现。

## 4. 计算引擎契约

### 4.1 输入与输出

原技术方案的计算入口为 `calculateOffer(offer, options)`。其职责按阶段组织：

```text
输入 Offer + 政策 + 用户假设
  → 薪资组成归集与总包对账
  → 社保公积金基数及个人／企业缴费
  → 年度个税（含年终奖两种计税口径）
  → 税后现金、非现金权益、企业用人成本
  → 现金储蓄、含权益储蓄
  → [后续] 有效时薪、情景与 3/10 年预测
```

方括号标记的能力**不构成 MVP 引擎必须实现的公开结果**。对金额运算应约定统一币种、周期与舍入边界；具体公式和数据类型在代码层落地时补充，不在本文件凭空给出未经确认的税率或计算结果。

### 4.2 薪资聚合和奖金

- 归集基本工资、职级工资、绩效、考核奖励、年终奖及一次性收入；每一组成部分保留周期、条件和应税属性信息。
- `BonusRule` 采用**可判别联合**，相应功能首次交付支持固定金额、绩效系数乘基数、阶梯（分档累进／分档区间）三类规则。互斥关系、触发门槛、层级和叠加是后续扩展点。
- 总包金额与明细合计构成**对账关系而非两个可累加收入项**。当二者不一致时返回差额及 warning，并保留用户选择的计算依据；界面不能暗自合并。
- 不确定奖金与一次性收入的应税判定不得丢失其来源或条件标记。

### 4.3 地区政策与社保

- `RegionPolicy` 按地区、适用年度查找；险种条目至少能描述个人与企业缴费比例、基数上下限、适用条件、来源链接及生效年度。
- 参保城市默认工作城市但可覆盖，政策年度默认入职年度。计算时按对应险种进行基数上下限约束，分别输出个人和企业金额。
- 未查到完整地方政策时返回**明确 warning**，改用带「全国通用样例」标识的配置，整体结果标注低置信度。该配置不可伪装为适用于该城市的真实法规。
- 政策文件按原方案置于 `src/policies/regions/`，每条应有官方来源链接，并维护已覆盖城市列表；首批可提供全国样例和少量有官方依据的城市种子文件。文件目录与已有仓库保持一致前需验证。
- 城市政策以 JSON 文件通过社区 PR 更新，不依赖后端或应用内政策共建分发服务。

### 4.4 个税与扣除

- 以**年度汇算口径**作为主要结果，可为将来月度累计预扣曲线预留单独输出；年终奖分别给出单独计税与并入综合所得的结果及差额，默认展示前者。
- 专项附加扣除采用 PRD-M04 已确认的住房租金参考方案，其余扣除项允许用户补充；输入必须携带用户是否确认及所适用的年度／条件，不得将预填参考值默认为法律资格已核实。
- 税率表及默认值按原方案由 `src/policies/` 的年度化数据维护，保留来源；选择逻辑和年份需核查政策生效条件，不把历史样例数值硬编码到计算函数。
- 补贴的税务归类使用可被用户覆盖的规则与来源信息；例如原需求所列的补贴归类仅为**待政策核实的默认示意**，不得不经核验直接固化为法规。

### 4.5 结果口径与比较

| 结果             | 计算或展示原则                                                   |
| ---------------- | ---------------------------------------------------------------- |
| 年度税后可用现金 | 由应计现金收入扣除个人缴费和个人所得税形成；按年度明确口径       |
| 现金储蓄         | 年度税后可用现金 − 年度现金生活成本                              |
| 含权益储蓄       | 现金储蓄 + 个人公积金入账；不加入医保个人账户                    |
| 企业用人成本     | 与个人实际到手分开输出，纳入企业缴费等雇主成本口径               |
| 医保个人账户     | 作为受限权益单列，不计入现金储蓄或含权益储蓄                     |
| 简版加权比较     | 同指标采用一致归一化和方向处理，并暴露权重、缺失值处理及排序口径 |

- 默认排序依据现金储蓄；含权益储蓄作为并列参考，不使用过时的「税后现金 + 公积金 − 生活成本」单一净储蓄指标。
- 比较服务应隔离正式 Offer 与工作区选择的预览数据；首版 MVP 只需正式 Offer 简版比较。
- 有效工时、通勤折算系数 0.5、年薪增长率 5%、CPI 3% 和无晋升等默认假设属于 PRD-F03／F04 的后续模型，应由可修改的假设配置提供，不固化为预测事实。

## 5. 存储、版本与数据交换

### 5.1 IndexedDB 持久化

- 数据库建议沿用 `offerithm`，通过仓储接口屏蔽视图层的 IndexedDB 操作；按领域对象和引用关系规划存储，而不是以页面状态为中心设计结构。
- schema 需版本化；升级应包含可回退／可中止的错误处理，不能用新版本默认值覆盖用户已确认的旧数据。
- 设计写事务时优先保证正式保存和草稿清理的一致性。涉及多个记录的导入应用也应避免出现无提示的部分覆盖；具体事务分块策略待实现阶段明确。

### 5.2 XLSX 多工作表交换（MVP）

- **格式职责**：单个 XLSX 工作簿代表数据库全量快照，不只是可视化的比较报表。
- **工作表职责**：按领域实体独立映射，例如 `Offer`、`Draft`、`Workspace`、`PreferenceProfile`、`Scenario`、`Settings`；具体字段和可选表由 `schemaVersion` 定义。尚未交付的能力可不产生数据行，不能把预留工作表误认为功能上线。
- **元信息**：至少携带 `schemaVersion`、导出时间、快照数据状态、计算口径说明，并能识别版本不兼容或不完整的数据。
- **导入阶段**：解析 → schema 与引用关系检查 → 冲突定位／差异预览 → 用户再次确认 → 写入。失败返回足够定位工作表及记录的错误信息，未确认不得修改现有数据。
- **关联完整性**：工作区的 Offer 引用、草稿与正式记录关联、偏好快照关系在导入导出后应保持一致。

原技术设计曾引用 `docs/adr/0001-excel-multisheet-data-interchange.md`，该 ADR 未包含在本次三份附件中；**目前不把其中未见到的具体字段设计视为已核实**。实现时应补齐交换 schema 规范及版本兼容策略。

### 5.3 JSON 与 CSV

- **JSON**：保留独立的机器友好型全量备份／恢复通道，产品方向已确认，但发布时间未单独锁定；优先复用同一领域校验与版本机制。
- **CSV**：用于未来面向分享的比较结果导出，明确**不在 MVP**；不承担全量数据库恢复职责。

## 6. UI 集成与非功能约束

- 展示层提供来源标签、warning、地区／年度、税务口径说明；不得仅在内部模型保留这些信息而不向用户展示。
- 根据 PRD 的 cafe 风格与响应式全功能要求选择组件库，并保持动效克制、语义明确；具体组件选型和设计 token 属于实现工作。
- 历史工作区、草稿恢复提示和工作区间正式事实隔离等交互必须通过清晰的页面状态流实现，不应由计算引擎自行维护 UI 状态。
- GitHub Pages 是原方案的持续部署目标，项目计划正式开源并补充 `LICENSE`、`README` 声明。此处仅记录既有方向，不宣称部署与文档已完成。

## 7. 技术待办与实现状态核查

1. **核查代码现状**：确认 `calculateOffer`、领域类型、仓储封装、路由、政策文件路径与依赖版本的真实状态；来源文档仅说明计算引擎「部分实现」。
2. **完善计算规格**：锁定数值精度／舍入、税务与社保明细规则、缺失输入行为；与可溯源的政策数据逐项核对。
3. **定义交换 schema**：完成 XLSX 领域对象字段映射、引用检查、版本兼容与冲突处理细则；同步更新必要 ADR。
4. **明确增量排期**：将 PRD 第 2.2／2.3 节的后续能力与 MVP 技术任务分开管理，避免「架构预留」被误认为「可验收功能」。
5. **落实验证**：可测性、测试分层和具体验收案例见 [测试计划](./test-plan.md)，不在此重复测试步骤。
